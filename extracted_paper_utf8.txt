Abstract—Running Large Language Models (LLMs) on con-
sumer edge devices is a major engineering hurdle because these
models require massive amounts of memory. Model quantization
helps solve this by compressing the file size, but we do not fully
understand how this compression impacts strict programming
tasks. Most benchmarks test if a compressed AI can still write
a good essay, but they don’t test if it can output strict JSON
payloads for backend APIs. In this study, we built an automated
benchmark using the 8B parameter Llama-3 model at both
8-bit and 4-bit quantization levels. We designed a scenario
based on an educational student marks analyzer, where the AI
had to extract grades from messy text and format them into
rigid JSON. Our results went against our initial assumptions.
The heavily compressed 4-bit model reduced inference time
by 71.2% (dropping from 3.10s to 0.89s) but miraculously
maintained a 100% accuracy rate for formatting. It didn’t drop
a single bracket or comma. We conclude that aggressive 4-bit
quantization is incredibly effective for edge-based data pipelines,
allowing developers to save massive amounts of local compute
power without breaking deterministic software logic.
Index Terms—Edge Computing, Small Language Models,
Quantization, Data Parsing, Autonomous Agents, JSON
I. INTRODUCTION
Right now, software engineers are rushing to integrate AI
into automated backend systems. LLMs are amazing at reading
unpredictable, messy human text and figuring out what it
means. But relying on huge cloud models (like OpenAI’s
GPT-4) brings up a lot of operational issues. Every time your
software makes an API call, you have to deal with network
latency, recurring costs, and most importantly, data privacy
risks.
This is especially true for educational software. If you
are building a platform like the EduMetrics student marks
analyzer, sending raw student grades to a third-party server can
violate strict data privacy laws. Because of this, developers are
shifting toward edge computing—running smaller AI models
locally right on the user’s laptop or server.
While running models locally is great for privacy, it is hard
on the hardware. To make a model fit on a normal computer,
we have to ”quantize” or compress it. But this brings up a
massive question for developers: if I compress this AI, will it
get too ”stupid” to follow strict coding rules?
If you ask an AI to extract data into a JSON dictionary,
it has to be perfect. If the AI hallucinates a conversational
phrase like “Here are your results!” before the JSON brackets,
the Python json.loads() function on the backend will
instantly crash. Most current research only tests if quantized
models can still speak English coherently. There is hardly
any empirical testing on whether they can still generate strict,
error-free data structures.
Our project fixes this gap. We built an automated pipeline to
benchmark a quantized local agent, aiming to see if developers
can safely trust 4-bit models to handle sensitive, rigid backend
automation.
II. BACKGROUND AND RELATED WORK
To really understand how we built this benchmark, it helps
to look at the mechanics of model compression and how
people normally test AI agents.
A. The Mechanics of Quantization
Under the hood, neural networks do all their thinking
using high-precision floating-point numbers (usually FP16).
Quantization takes those big, precise numbers and rounds them
down to lower-precision integers, like INT8 (8-bit) or INT4
(4-bit). It is very similar to compressing a high-quality image
into a smaller JPEG. You lose some detail, but the file size
shrinks dramatically.
A few years ago, researchers like Dettmers et al. showed
that dropping a model to 8-bit precision barely hurts its
predictive power at all. Today, thanks to community projects
like Llama.cpp and Ollama, developers can run these com-
pressed models natively on standard CPUs and GPUs. But
while the open-source community loves quantization, aca-
demic benchmarks usually only test these models on reading
comprehension or trivia questions. They don’t test them on
software engineering tasks.
B. Testing AI as Software Agents
Lately, the tech industry has been moving toward using
LLMs as “agents.” Instead of just chatting with users, an
agent is an AI that runs in the background, interacting with
databases or formatting code. Frameworks like AgentBench
exist to test how well AI can use tools, but they almost
exclusively focus on massive, uncompressed cloud models.
Our benchmark isolates the specific variable of quantization.

To simulate a real edge computing environment, we did not
use a cloud server. We ran everything locally on a consumer-

completely eliminated internet lag, ensuring our latency mea-

B. Synthetic Dataset Generation
Because we needed data that mimicked a real educational
platform, we couldn’t just use standard benchmarking text.
We wrote a custom Python script using the pandas library to
generate 100 unstructured text strings. The script was designed
to introduce linguistic “messiness”—like bad grammar or
confusing sentence structures—to force the AI to really think
about data extraction.

C. Prompt Engineering Strategy
We decided to use a zero-shot prompt. This means we did
not give the AI any examples of the correct answer; we just
gave it instructions and the messy text. The prompt acted as
a strict system constraint.
The most important part of our prompt was the negative
constraints. We explicitly wrote: “Extract the student name
and scores. Output the result STRICTLY as a valid JSON
object. Do NOT output any conversational text. ONLY output
the JSON block.” We needed to test if the 4-bit model still had
enough parameter “attention” to suppress its natural training
as a helpful chatbot.
D. The Automated Pipeline

IV. ENGINEERING CHALLENGES AND SYSTEM STABILITY
While building this testbench, we ran into a massive hard-
ware limitation that perfectly highlights the reality of edge
computing. When we initially wrote the script, we designed
it to test Row 1 on the 4-bit model, load the 8-bit model for
Row 1, and then swap back. When we executed this, the script
completely crashed our local server before finishing Row 0.
Hot-swapping multi-gigabyte neural networks in and out of
active RAM caused an intense Out of Memory (OOM) error.
To resolve this severe RAM spike, the execution flow was
refactored to process all 100 rows sequentially on the 4-bit
model, flush the system memory, and then execute the 8-bit
benchmark. We also wrapped the calls in a try/except
block so localized server timeouts wouldn’t destroy our exper-
iment data. This hardware roadblock demonstrates why model
size management is absolutely critical on consumer devices.
V. RESULTS AND DISCUSSION
Going into the experiment, we strongly hypothesized that
dropping down to 4-bit precision would cause the AI to occa-
sionally forget its instructions and break the JSON formatting.
The actual data proved us completely wrong.
A. Formatting Accuracy and Logical Resilience
Surprisingly, both the 8-bit baseline and the 4-bit com-
pressed model achieved a perfect 100.0% success rate across
the dataset. We didn’t see a single JSONDecodeError. Even
at half the bit precision, the 4-bit Llama-3 model successfully
handled syntax, bracket matching, and the negative prompt
constraints. It seems that the logic circuits inside the neural
network that handle structural formatting are incredibly re-
silient to integer rounding.

B. Inference Speed and Resource Efficiency
While accuracy stayed the same, the processing speed
changed drastically. The 8-bit baseline model recorded an
average inference latency of 3.10 seconds per row. During
this test, we observed that the computer’s fans were running
loudly and the system was working hard.
When we ran the 4-bit model, it processed the exact same
task with an average latency of just 0.89 seconds. That is a
71.2% reduction in generation time, and the system ran much
cooler. If an educational platform needed to process a batch of
100 student records locally, the 8-bit model would take over
five minutes to finish. The 4-bit edge model would get it done
in under 90 seconds.

C. What This Means for Edge Architecture
This data is a huge win for developers. It proves that you
don’t need a massive, high-precision model just to do offline
data extraction. While 4-bit compression might ruin an AI’s
ability to solve complex calculus or write nuanced essays,
it functions perfectly as a high-speed logic filter. Developers
building privacy-first applications can confidently use these
tiny models for backend tasks, saving memory and battery
life without risking a pipeline crash.
VI. LIMITATIONS AND FUTURE WORK
While our results demonstrate strong agentic reliability for
4-bit models, the dataset was limited to 100 synthetic rows
with a flat, simplistic JSON schema. Future testing should
expand to larger datasets with complex, nested JSON arrays
to see if the compressed model can handle multi-step reasoning
before formatting. Additionally, future benchmarks should
evaluate even more aggressive compression architectures, such
as 2-bit or 1-bit frameworks, to identify the exact threshold
where syntactical logic finally breaks down.
VII. CONCLUSION
Putting AI agents on consumer laptops or IoT devices is
always a trade-off between intelligence and hardware limits.
The data from our Python testbench shows that choosing 4-
bit quantization isn’t really a sacrifice at all when it comes
to standard backend parsing. By keeping a flawless 100%
logical accuracy rate while making processing speeds over
70% faster, 4-bit models prove they are more than capable
of handling repetitive data extraction. They are essentially the
optimal choice for building secure, fast, and local automation
tools in modern software development.
